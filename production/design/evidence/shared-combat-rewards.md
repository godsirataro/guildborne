# Optional shared combat rewards binding

Status: private source implementation and local fixtures, **not activated**. No Bootstrap, World, runtime flag, remote, cloud provider, respawn or second Heartbeat was added. Candidate binding remains coordinator-owned after review.

`SharedCombatRewards(deps)` consumes `Policy`, opaque `EncounterToken`, one exact basic `Enemy`, monotonic `Now`, server-fixed `EncounterId`, `RotationSeed`, `Budget={xp,gold,items}`, `OwnerRoster(ownerId)`, `MakeParticipation`, `Settlement`, validating version-2 `Repository`, existing durable-claim `Delivery`, and `Util`. Budget is copied and validated at construction; no economic amount is generated by this adapter. Enemy MaxHealth fixes the provisional participation threshold before combat.

Synchronous `Observe(event,a,b,effectiveAmount)`, `Recover(actor,effectiveAmount)` and `Leave(ownerId)` perform only bounded memory work. Relevant damage/healing receive one increasing event sequence; positive effects credit the existing participation module. Neutral Hero recovery consumes wounds without credit. Enemy recovery is ignored by the Hero-wound ledger. CombatDamage emits enemy_defeated after the lethal damage event, so the exact registered enemy at zero HP freezes eligibility once after the lethal credit. Foreign/repeated death events cannot prepare another allocation. An empty eligible set produces no settlement.

**Experimental conservative roster policy:** freeze an owner's canonical player-plus-up-to-five actor IDs at their first accepted positive contribution, then require the final participation threshold/activity/grace eligibility before including that owner. Actor additions after that first contribution never enlarge their XP roster. A legitimate new owner registration can resume earned contribution but retains that original roster. Departed qualifying owners retain it through the bounded grace. Invalid/missing trusted rosters fail the entire snapshot; there is no redistribution. This policy is explicit design under test, not a Public balance claim.

`SharedCombatCoordinator` optionally calls `MakeRewards({Policy,EncounterToken,Enemy,OwnerRoster})` after registry enemy registration. Its roster callback checks exact current Player/profile session object, token/epoch, character, selected roster and actor membership before returning IDs. Leave runs before registry revocation. The supplied Observe/Recover become the shared context sinks. HeroService forwards MakeRewards and exposes `PumpSharedRewards`/`SharedRewardState`; no Heartbeat invokes Pump. Existing integrations without MakeRewards retain their sinks.

`Pump()` is an explicit potentially yielding worker entrypoint. It never runs from a combat sink. It prepares or resolves the same frozen snapshot through the injected validated repository, verifies exact expected allocation, and only then calls existing `Delivery.Deliver` for one recipient per invocation. A single-flight guard prevents overlapping workers. Recipient round-robin retries mean one full inventory cannot starve other owners. Delivery idempotency/session fencing comes from the existing SharedPvERewardAdapter and PlayerDataService durable claim path, not a new grant implementation. Unknown preparation/worker exceptions do not deliver early and preserve the candidate for retry. Conflict fails closed. No MarkDelivered or cross-profile atomicity is claimed.

`Close()` rejects further combat observations but retains a frozen pending settlement and recipient delivery state. Pump can finish that already-authorized work after scene closure; closing before a death snapshot produces no new settlement. Memory state is bounded to one encounter, sixteen rosters and sixteen delivery entries. The underlying repository/profile 32-record/receipt limits and recovery discovery still require launch-scale design; there is no eviction or automatic respawn here. Root must own a bounded deferred worker and session cleanup for the injected Delivery adapter if this is later enabled.

## HeroService explicit shutdown

`HeroService.Destroy()` is an idempotent terminal lifecycle operation, invoked by its owning runtime between combat updates. It disconnects the retained Heartbeat connection, removes every owned runtime session through the existing `Remove` path (shared identity detach, character listener disconnect, regional scenes, hero/enemy models and hero folders), closes the optional shared coordinator and destroys its own away folder. It does not destroy player Character models or caller-owned plots. Existing asynchronous path computations are fenced by `s.alive=false` and hero generation increments. Mutating creation/update entrypoints reject or no-op after destruction, preventing recreation of orphan sessions/models.

The optional shared coordinator remains referenced so `SharedRewardState` and external `PumpSharedRewards` can finish already-frozen pending rewards. Destroy performs no profile writes or delivery itself. Closure before finalization cannot create a settlement. Calling shutdown from a combat effect callback is outside this lifecycle contract; the owner invokes it between updates.
