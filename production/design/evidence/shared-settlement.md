# Shared PvE settlement preparation — local contract

Status: source implemented; focused local validation only. No runtime binding, remote, DataStore provisioning, profile mutation, payout, MarkDelivered, receipt acknowledgement, or release flag is included.

`SharedPvESettlement.Build(snapshot)` returns `record, nil` or `nil, reason`. The exact snapshot shape is `{version=1, encounterId, owners, rotationSeed, xp, gold, items}`. Owners is a dense unique array of signed nonzero integer user IDs (absolute maximum 2^53−1); negative IDs support Studio clients consistently with the identity registry, while real Players normally use positive IDs. Sign does not authorize participation. Items is a dense array of `{itemId,count}`. IDs use ASCII alphanumeric/underscore/hyphen, length 1–64. Item IDs are syntactically validated here; the trusted encounter authority must additionally resolve canonical item definitions and eligible owners before constructing a snapshot. This module never accepts a client reward claim.

Limits: 1–16 eligible human owners (16 is a fixture/contract admission bound, not measured server capacity; covers a six-player Party plus solo outsiders), 0–32 item types, XP/gold each 0–1,000,000,000, each item count 1–1,000,000, rotation seed 0–2,147,483,647. NaN, nonintegers, overflow, sparse arrays, duplicates and unknown fields reject. Owners and item types are sorted; input order does not affect output. The server-fixed seed rotates remainder ownership; the cursor advances across XP, gold and sorted item types. Each resource differs by at most one between owners and totals exactly conserve the finite encounter budget. Allocation is per owner; division between that owner's player and NPC heroes is explicitly unresolved and outside this module.

`SharedPvESettlementStore(store, util, settlement, namespace)` accepts the existing `Read(key)`/atomic `Update(key,transform)` provider contract and TableUtil. It provides `Prepare(snapshot)` and `Read(encounterId)`, returning `record?, status, reason?`. Prepare returns Prepared for a new or identical canonical allocation; changed owners, budget or seed conflict. Read returns Found or Missing. Provider failures return Unavailable; a write error is WriteUnconfirmed because it may already have committed. Retrying Prepare or Read resolves the stored immutable allocation. Every outward record is a deep copy.

All records share one atomic `shared-pve-v1:<namespace>` bucket. Namespace is 1–24 safe characters. Capacity is **32 records** and returns Capacity when full; it never evicts or forgets pending records. This intentionally bounded repository is not a launch-scale retention strategy. A separately reviewed archival/receipt design is required before production use. Two repository instances using the same injected provider and namespace share the same authority. Separate namespaces isolate records. Existing records are structurally reconstructed and compared before trusting the bucket. Update callbacks have no external effects and may retry against changed state.

## Experimental v2 frozen actor XP subdivision

Version 1 remains the original shape and algorithm with no new fields. Version 2 adds required `xpPolicy="equal-actors-v1"` and replaces each numeric owner entry with `{ownerId,actorIds}`. Each dense unique actor array contains exactly one literal `player` and zero through five other actor IDs; IDs are 1–64 ASCII alphanumeric/underscore/colon/hyphen characters. Canonical profile membership and real actor eligibility remain the trusted snapshot producer's responsibility. This validator cannot infer roster ownership from an ID string.

Owners sort by ownerId and actor IDs sort lexically. First, the encounter XP budget is divided between owners using the unchanged conserved owner allocation. Then each owner XP share is subdivided equally between their frozen actor IDs, using `rotationSeed % actorCount` for deterministic remainder rotation. Each v2 allocation adds `actorXP={[actorId]=integer}` including zero shares. The sum of actorXP equals that allocation's xp exactly; actor count never multiplies encounter XP. Gold/items still belong to the owner allocation. This is a **provisional policy contract**, not a profile XP grant or approved balance outcome.

Repository factory gains optional fifth argument `version` (default 1). Version 2 uses a separate `shared-pve-v2:<namespace>` key and bucket version 2. It rejects v1 payloads, while the default v1 repository rejects v2 payloads. No migration or rewriting of v1 records occurs. Roster changes under the same encounter ID conflict with the frozen record. Retry and uncertain-after-commit recovery apply to both versions. Capacity remains 32 records; the 2,048-value/depth-8 per-record guard accepts the tested maximum v2 shape (16 owners × 6 actors, 32 item types) across a full 32-record bucket. This is a bounded fixture, not measured cloud throughput or a production retention scheme.
