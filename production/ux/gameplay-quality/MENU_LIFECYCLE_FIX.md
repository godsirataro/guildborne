# Map / Management presentation gate

Controller observed Map open -> Management open -> N closes Map, leaving Management visible while combat controls reappeared. Readback had ManagementPanel.Visible=true, GuildborneMenuOpen=true and a separate MenuRouter.isBlocking()==false. This occurred in independently loaded client-review modules, where cached router registries may differ. It is not yet a reproduced clean whole-build production regression.

Later controller whole-build b35d377 inspection after BeginAdventure and N showed Management visible, Map hidden and combat health/buttons/selection hidden with a clean screenshot. Tool-side require(MenuRouter).isBlocking() still returned false. Therefore that tool require result is not proof of the running LocalScript's router state. This patch is scoped adapter-resilience hardening and preservation of normal menu behavior, not a claimed repair of a proven production router defect.

GameplayMenuGate is a small shared UI helper, not a service or authority change. It reads the router result, existing PlayerGui GuildborneMenuOpen attribute and visible ManagementPanel under enabled GuildborneUI. PlayerCombatController uses it for HUD visibility and dispatch-time guards (send, cycle and direct actor selection). CityNavigation uses the same gate. Map toggling closes its own visible panel first; opening is refused while a menu blocks, including the interval before toggle visibility refreshes. N checks focused text input and can close a visible map even when its toggle is hidden. Quest route selection is not cleared.

The helper never writes or clears GuildborneMenuOpen. Normal menu-owner lifecycle clears that attribute; tests cover clearing the flag while Management stays visible and eventual menu close restoring access. A permanently stale true flag from an external owner would still block by design and requires that owner's lifecycle repair, rather than silently bypassing another menu. Fresh-build validation is needed to determine whether such an owner issue exists.
